# v0.2 model decision

## Baseline (Task 42, 2026-10-12)

unanswerable questions; `v02-answers.jsonl`: 40 answerable and 20 unanswerable
probes) with the default models, before any retrieval change. The set is
model-authored and model-reviewed, not human-checked (D-018).

- Machine: Apple M5 Max, macOS (Metal)
- Version: `orag 0.2.0-alpha.16` with the Task 42 harness (release build; merged as 0.2.0-alpha.18)

### What the baseline shows

- **Fusion loses cross-language questions.** Dense retrieval alone puts the
  evidence of 22 of 25 cross-language questions in the answer context (0.880);
  hybrid only 15 (0.600). The lexical list finds nothing useful when the
  question and the document share no words (0.280), yet its top hits take
  context slots and its leader is promoted to the front. This is the largest
  gap in the set and the first thing a fusion change has to fix.
- Hybrid misses 20 questions in context; 12 of them dense alone finds (v2-fac-011, v2-md-006, v2-md-016, v2-md-017, v2-tab-015, v2-xl-001, v2-xl-005, v2-xl-018, v2-xl-021, v2-xl-022, v2-xl-023, v2-xl-025), and dense misses 15 that hybrid finds (v2-acc-006, v2-acc-012, v2-fac-003, v2-fac-017, v2-fac-028, v2-fac-035, v2-fac-039, v2-id-006, v2-id-009, v2-id-011, v2-id-014, v2-md-008, v2-md-013, v2-md-020, v2-tab-007). Both lists matter; how they are fused decides.
- Identifiers and tables are found well (0.920, 0.960 in context); their MRR
  (0.770, 0.748) leaves room for ranking, not for recall.
- Accentless questions are all found in context (1.000), because the dense side
  reads them; lexically 0.950.
- Holdout trails dev (hybrid in context 0.862 vs 0.909). Changes are tuned on
  `dev` and adopted only when `holdout` does not drop (D-018).
- Answers: 34 of 40 answerable probes complete, 5 refused although answerable,
  17 of 20 unanswerable ones refused.

## Decision rule (Task 44, written before any candidate is scored)

Written on 2026-10-12, before the first scoring run of a candidate embedder or
generator. It is not changed after the numbers are in.

**Embedder.** Candidates: `multilingual-e5-large-instruct-q8_0` and
`bge-m3-q8_0` against the default `qwen3-embedding-0.6b-q8_0`. A candidate is
scored only if it passes qualification (`tests/embedder_qualification.rs`):
finite unit vectors of 1024 dimensions, token counts within ±2 of the
reference tokenizer, the relevant passage first in at least 9 of 10 triples,
and Metal and CPU vectors with cosine ≥ 0.999. One that fails is reported as
"not qualified at llama-cpp-2 0.1.158" and not scored.

The default changes only if a qualified candidate, with **hybrid** retrieval
and paired per question (recall@10 hit or miss):
1. wins minus losses ≥ 6 on the **dev** split of `v02-retrieval.jsonl`;
2. wins minus losses ≥ 0 on **holdout**;
3. no category loses more than 2 questions net (dev and holdout together);
4. query-embedding p95 ≤ 2 × the current default's;
5. `orag serve` RSS after indexing grows by ≤ 1.5 GB.
Otherwise the default stays Qwen3-Embedding-0.6B. Wins and losses are
reported per category, not only as averages.

**Generator.** With retrieval fixed (the default embedder, the same top-k
contexts), `qwen3-4b-instruct-2507-q4_k_m` replaces `qwen3.5-4b-q4_k_m` only if
on `v02-answers.jsonl` (sampler `dry`): expected-fact wins minus losses ≥ 4
probes, **and** no more `repetition` or `length` finishes, **and** abstention
F1 is not lower.

**Fusion** is not part of this rule: the cross-language finding above is a
retrieval change, decided on its own and measured on the same dev/holdout
split, after the model decision.

## Decision (Task 44, 2026-10-12)

**Result: no model changes for v0.2.** The default embedder stays
`qwen3-embedding-0.6b-q8_0` and the default generator stays
`qwen3.5-4b-q4_k_m`: no candidate met the rule written above before scoring.

Setup: release build of 0.2.0-alpha.21 on Apple M5 Max (Metal), every pack
imported with SHA-256 verification into a separate models folder;
`orag eval retrieval` on `v02-retrieval.jsonl` (200 questions: 175 answerable,
25 unanswerable; 12 documents) and `seed.jsonl`; `orag eval answers` on
`v02-answers.jsonl` with sampler `dry`.

### Qualification (`tests/embedder_qualification.rs`)

Run on Metal and, in a Linux arm64 container, on CPU; the CPU run compares
its vectors with the Metal ones (`ORAG_TEST_BACKEND_VECTORS`).

| check | bge-m3-q8_0 | multilingual-e5-large-instruct-q8_0 |
|---|---|---|
| 1024-d finite unit vectors | pass | pass |
| llama.cpp token counts vs reference tokenizer (±2) | equal (11, 13, 14, 8, 8) | equal (11, 13, 14, 8, 8) |
| relevant passage first, predeclared set (≥ 9 of 10) | 10 of 10 | 10 of 10 |
| Metal vs CPU cosine ≥ 0.999 (5 documents, 5 queries) | pass (min 0.99960) | pass (min 0.99983) |

Both qualified. The predeclared ranking set is weak: its distractors are off
topic, so near-random multilingual encoders could pass it too. A second set
with hard negatives (same topic and language, wrong fact: another period,
error code or rule) was added after scoring, during review. It does not
separate the v0.2 models: the default and both candidates rank 8 of 10 (each
fails the cross-language return-period pair and one other), so it gates a
candidate at "at least as good as the default" (≥ 8 of 10) and leaves the
predeclared rule as it was.

Packs: `bge-m3-q8_0` from `ggml-org/bge-m3-Q8_0-GGUF` at
`9eba04c5d75ba5a1595e45de734d36bef4e5cb98` (CLS pooling, no prefixes);
`multilingual-e5-large-instruct-q8_0` from
`Ralriki/multilingual-e5-large-instruct-GGUF` at
`f43c843a00e7c3bdd087cbaf481464c1fa7fb37d` (mean pooling, max 512 tokens,
the instruct query prefix); no author GGUF exists for e5, so the most used
conversion was taken. Both are MIT, declared only in the model card of the
original repository (no LICENSE file there): a pack ships that card as
`MODEL_CARD.md` and the MIT text as `LICENSE`. bge-m3 was scored with
`max_tokens = 8192`; the preset now sets 1024 (the context the embedder
allocates; no chunk or query comes near it), which re-scores identically.
Chunks are never cut: the chunker sizes them to the embedder's room
(`effective_chunker`, Task 14) and `embed_text` returns an error instead of
truncating, so no truncation counter was added (plan Step 2).

### Retrieval (hybrid unless noted)

| embedder | recall@5 | recall@10 | MRR@10 | nDCG@10 | in context | dense recall@10 | dev recall@10 | holdout recall@10 |
|---|---|---|---|---|---|---|---|---|
| qwen3-embedding-0.6b (default) | 0.829 | 0.891 | 0.679 | 0.774 | 0.886 | 0.886 | 0.909 | 0.874 |
| bge-m3 | 0.891 | 0.937 | 0.748 | 0.838 | 0.914 | 0.931 | 0.943 | 0.931 |
| e5-large-instruct | 0.840 | 0.869 | 0.678 | 0.769 | 0.863 | 0.851 | 0.898 | 0.839 |

Lexical alone differs a little per embedder because each tokenizer cuts
chunks differently (recall@5 0.754 default, 0.737 for both candidates).

Cost, measured after review on a second, warm pass (each model scored twice
in turn; the first, cold pass ran the default first and inflated its
latency): retrieve latency is the whole hybrid `retrieve()` call (query
embedding, lexical search, fusion, store reads), not the query embedding
alone. Serve memory is `orag serve` (with the default generator loaded)
after indexing the twelve v0.2 documents, on Metal; GPU buffers are not all
counted in RSS, and CPU or Windows builds were not measured.

| embedder | retrieve p50 / p95 | chunks | index time | serve RSS idle → indexed |
|---|---|---|---|---|
| qwen3-embedding-0.6b (default) | 13.0 / 13.8 ms | 274 | 7 s | 3.79 → 4.11 GB |
| bge-m3 | 10.5 / 11.0 ms | 212 | 4 s | 3.78 → 4.29 GB (+0.18) |
| e5-large-instruct | 10.8 / 11.5 ms | 213 | 5 s | 3.75 → 4.26 GB (+0.15) |

On `seed.jsonl` all three reach hybrid recall@10 1.000.

Paired per question against the default (hybrid recall@10 hit or miss):

| candidate | dev wins / losses (net) | holdout wins / losses (net) | per category (wins / losses) |
|---|---|---|---|
| bge-m3 | 4 / 1 (**+3**) | 6 / 1 (+5) | cross_language 5/1, factual 3/0, identifier 2/0, multi_document 0/1 |
| e5-large-instruct | 4 / 5 (−1) | 4 / 7 (−3) | cross_language 3/5, factual 3/2, identifier 2/0, multi_document 0/5 |

| rule | bge-m3 | e5-large-instruct |
|---|---|---|
| dev net ≥ 6 | **no (+3)** | no (−1) |
| holdout net ≥ 0 | yes (+5) | no (−3) |
| no category below −2 net | yes (−1) | no (multi_document −5) |
| retrieve p95 ≤ 2 × default (query p95 not measured alone) | yes | yes |
| serve RSS growth ≤ 1.5 GB (Metal) | yes (+0.18 GB) | yes (+0.15 GB) |

**bge-m3 misses the switch rule on dev (+3 of the 6 needed)**, although it is
better on every hybrid and dense headline number and on holdout (not on
lexical alone, nor on multi-document questions, 0 wins / 1 loss), and it is
the only candidate that
helps the weakest category (cross-language, net +4). The rule was written
before scoring and is not relaxed after it. It stays the first candidate when
the default is next reconsidered, together with the fusion change below:
**e5 is rejected** (worse on holdout and on multi-document questions).

### Generator (retrieval fixed: default embedder, same contexts)

| generator | expected facts | cited evidence | valid citations | abstention P / R (F1) | finishes | p50 / p95 | RSS |
|---|---|---|---|---|---|---|---|
| qwen3.5-4b (default) | 0.850 | 0.825 | 1.000 | 0.773 / 0.850 (0.810) | 59 stop, 1 length | 1.5 / 5.7 s | — |
| qwen3-4b-instruct-2507 | 0.750 | 0.750 | 0.941 | 0.654 / 0.850 (0.739) | 60 stop | 1.1 / 2.8 s | 4.99 GB |

Expected-fact wins / losses of 2507 against the default: 0 / 4 (net −4; the
rule needs +4), its abstention F1 is lower, and not every answer cites
validly. **The default generator stays.** 2507 is faster (p95 2.8 s vs 5.7 s),
which does not enter the rule.

### Next

The largest gap is still fusion on cross-language questions (hybrid in
context 0.600 vs dense alone 0.880 with the default embedder). That is a
retrieval change, decided on its own on the same dev/holdout split. A later
model review starts from bge-m3 and re-runs this rule; a bigger, human-checked
set (D-018) would let a +3 on dev count for more than noise.
