# v0.3 fusion change (step 48)

The v0.2 baseline (`v0.2-model-decision.md`) found that hybrid retrieval loses
cross-language questions that dense retrieval alone finds: with the default
embedder, cross_language in context is 0.600 under hybrid and 0.880 under
dense alone. This document records the fusion change made for it.

## Decision rule (written on 2026-10-13, before any variant is scored)

It is not changed after the numbers are in.

Variants are scored with `orag eval retrieval` on
`eval/corpus/v02` + `v02-retrieval.jsonl`, default models, hybrid strategy.
Tuning looks at the **dev** split only; holdout is read once, for the chosen
variant. Paired per question on "in context" (every required label within the
answer context), against the current fusion (RRF k = 60, equal weights, list
leaders promoted).

The chosen variant replaces the current fusion only if:
1. wins minus losses ≥ 4 on **dev**;
2. wins minus losses ≥ 0 on **holdout**;
3. no category loses more than 2 questions net (dev and holdout together);
4. `seed.jsonl`, `anayasa-tr.jsonl` and `anayasa-cekim-tr.jsonl` lose at most
   1 question net each on hybrid in context;
5. it adds no model call and no new index (fusion only).

Otherwise the current fusion stays and the result is recorded here.

## Result (2026-10-13): adopted

**Change:** each list's top 4 hits (`RetrievalConfig::leaders_per_list`: half the 8-chunk context) lead the fused order,
in two tiers: both lists' #1 first, then their #2-#4, each tier in RRF order;
the rest follow. Before, only each list's #1 was promoted (D-005). RRF itself
(k = 60, equal weights) is unchanged. Four per list fill the 8-chunk answer
context when the lists do not overlap; the #1 tier keeps a smaller context
(a tight token budget) starting with both leaders, as before.

Setup: release build on Apple M5 Max (Metal), default models
(`qwen3-embedding-0.6b-q8_0`, `qwen3.5-4b-q4_k_m`), the commands in
`v0.2-model-decision.md`.

### Variants scored on dev (paired against the current fusion)

Weighted RRF (`score = Σ w / (k + rank)`) with the list leaders promoted
(`p1`) or not (`p0`), then deeper promotion (`rN`: each list's top N lead):

| variant | dev wins / losses (net) |
|---|---|
| k 60, dense weight 1, p0 | 0 / 2 (−2) |
| k 60, dense weight 1.5, p1 | 0 / 0 (0) |
| k 60, dense weight 2, p1 | 1 / 0 (+1) |
| k 60, dense weight 3, p1 | 2 / 1 (+1) |
| k 20, dense weight 1, p1 | 1 / 0 (+1) |
| k 20, dense weight 1.5, p1 | 2 / 0 (+2) |
| k 20, dense weight 2 or 3, p0 or p1 | at most +2 |
| k 60, dense weight 1, r2 | 1 / 0 (+1) |
| k 60, dense weight 1, r3 | 3 / 0 (+3) |
| **k 60, dense weight 1, r4** | **4 / 0 (+4)** |
| k 20 or dense weight 1.5, r4 | 4 / 0 (+4), no better |

Dev had 5 answerable questions that hybrid missed and one list alone found,
so +4 is near the ceiling for a fusion-only change. Weighting the dense list
does not reach it: the lexical list's incidental matches still outscore a
dense #4 on cross-language questions. The simplest variant at +4 (no new
constant besides the depth) was chosen; holdout was read for it only.

### Rule check

| rule | result |
|---|---|
| dev net ≥ 4 | yes (+4: cross_language +2, multi_document +2) |
| holdout net ≥ 0 | yes (+6: 7 wins, 1 loss) |
| no category below −2 net | yes (worst: factual −1) |
| seed / anayasa-tr / anayasa-cekim-tr lose ≤ 1 | yes (0 / 0 / −1: in context 0.900 → 0.867) |
| fusion only | yes |

### Retrieval, `v02-retrieval.jsonl`, hybrid

| | recall@5 | recall@10 | MRR@10 | nDCG@10 | in context |
|---|---|---|---|---|---|
| before | 0.829 | 0.891 | 0.679 | 0.774 | 0.886 |
| after | 0.880 | 0.949 | 0.693 | 0.797 | 0.943 |

| category (in context) | before | after |
|---|---|---|
| cross_language | 0.600 | 0.840 |
| multi_document | 0.850 | 1.000 |
| identifier | 0.920 | 0.960 |
| table | 0.960 | 1.000 |
| factual | 0.925 | 0.900 |
| accentless, inflection | 1.000, 0.950 | unchanged |
| dev / holdout | 0.909 / 0.862 | 0.955 / 0.931 |

Retrieve latency is unchanged (p95 13.7 ms against 14.5 ms).

### Answers, `v02-answers.jsonl`, sampler `dry` (not part of the rule)

| | expected facts | cited evidence | valid citations | abstention P / R | p50 / p95 |
|---|---|---|---|---|---|
| before | 0.850 | 0.825 | 1.000 | 0.773 / 0.850 | 1.1 / 2.7 s |
| after | 0.925 | 0.900 | 1.000 | 0.941 / 0.800 | 1.6 / 3.5 s |

Cross-language probes answered with the expected facts: 2 of 5 → 5 of 5.
The costs: one more unanswerable probe is answered instead of refused
(recall 0.850 → 0.800), and answers take about 0.5 s longer, because the
context now holds more distinct chunks (more prompt tokens). Both are watched
when the generator or the context size is next changed.

Known trade-off (code review): a chunk that both lists rank just below their
top 4 (say #5 in each) has the best fused score but now sorts after up to
eight single-list hits, so it can miss the 8-chunk context. The factual −1
and anayasa-cekim −1 above are consistent with that. It is not tuned away
here: holdout was read once, for the variant chosen on dev, and a change made
after reading it would be chosen on holdout. A later fusion change can start
from it (for example, keep consensus hits within the first context).

The depth is half the answer context (`RetrievalConfig::leaders_per_list`,
`max_context_chunks / 2`), so a smaller or larger context keeps the two lists
sharing it evenly.
