# v0.4 embedder decision: bge-m3 (step 66)

bge-m3 (`bge-m3-q8_0`, MIT, 1024-d) has been the first challenger since Task 44: better on every
headline number, but short of Task 44's gate twice (v0.2 dev recall@10 W−L +3, then +5 in step 59,
against +6). Step 65 showed a reranker adds one net dev point on top of it, so the embedder is the
remaining v0.4 retrieval lever. Everything bge-m3 has been measured on so far (v0.2 dev and
holdout, the protection sets) has been read; only the v0.4 holdout (`v04-holdout-*.jsonl`, step 60)
has not. This rule therefore gates on the v0.4 holdout and treats the v0.2 numbers as checks that
must not regress, not as the evidence.

## Decision rule (written on 2026-10-15, before the v0.4 holdout is read)

It is not changed after the numbers are in. gpt-6-sol (high) reviewed the first draft and asked for
four changes, all taken: a CPU gate with a Windows smoke run, repeated cost measurements on read
data, answers gated per set, and the disk cost in the record.

**Quality runs** (read the v0.4 holdout once per embedder), on the 0.3.0-alpha.18 engine,
M-series Mac (Metal), default lexical mode, context budget on, no reranker:
`orag eval retrieval` with `qwen3-embedding-0.6b-q8_0` (default) and `bge-m3-q8_0` on
`v04-holdout-retrieval.jsonl` (`eval/corpus/v02`); `orag eval answers --sampler dry` with each
embedder on `v04-holdout-answers.jsonl`. Plus, on data already read: `v02-retrieval.jsonl`,
`seed`, `anayasa-tr`, `anayasa-cekim-tr` and `v02-answers.jsonl`.

**Cost runs** (only read data; repeated): `orag eval retrieval --no-context-budget` on
`v02-retrieval.jsonl` three times per embedder under `/usr/bin/time -l`. The run indexes the 12
v0.2 documents from empty and then answers 200 questions three ways, so its wall time is mostly
indexing. Reported: the median wall time, the median hybrid p95, and the largest "peak memory
footprint" (which on Apple silicon includes the Metal allocations).

**CPU runs** (`.github/workflows/model-cpu.yml`, pushed on a `bench/**` branch, release build,
both embedders fetched with `scripts/fetch-model-pack.*`): on GitHub's x86-64 `ubuntu-22.04` runner
(4 vCPU, 16 GB), the same cost run once per embedder on `v02-retrieval.jsonl`; on
`windows-latest`, bge-m3 is loaded, indexes `eval/corpus/seed` and answers `seed.jsonl`.

**Adopted as the default embedder only if all hold:**
1. v0.4 holdout, hybrid in context, paired per question: W−L ≥ +3 (88 answerable questions; a
   practical-gain threshold, about 3.4 points, not a significance test);
2. v0.4 holdout, hybrid recall@10: W−L ≥ 0;
3. no category loses more than 1 net in context on the v0.4 holdout, and factual + identifier +
   table lose nothing net there;
4. v0.2 (all rows) hybrid in context W−L ≥ 0, and `seed`, `anayasa-tr`, `anayasa-cekim-tr`
   lose at most 1 each in context;
5. answers, gated **per set** (`v02-answers.jsonl` and `v04-holdout-answers.jsonl` separately):
   expected facts lose nothing net after a per-probe review of scorer artefacts; on the v0.4 set,
   cited evidence loses nothing net; abstention, counted per probe as unanswerable probes that
   flip from refused to answered (or answerable from answered to refused) minus the reverse, loses
   at most 1 per set; and no probe gains an unsupported answer or an invalid citation;
6. Metal: median hybrid p95 of the cost runs ≤ the default's + 20 ms;
7. Metal: median cost-run wall time ≤ 1.5× the default's, and the largest peak memory footprint
   grows by ≤ 512 MB;
8. CPU (x86-64 runner): hybrid p95 ≤ 2× the default's (Task 44's query-latency bound); the
   wall-time ratio is reported;
9. Windows: the bge-m3 smoke run finishes and its hybrid recall@10 on `seed` is not below the
   default's on the same runner.

Also recorded, not gated: the model pack sizes on disk and whether the README's free-space
requirement still holds for install plus one reindex; the vectors stay 1024-d, so the index size
does not change. MIT license and `LICENSE` file in the pack are verified as in Task 44.

If all hold, `bge-m3-q8_0` becomes the default in the model pack, config template, installer and
docs; the release note says every existing collection must be reindexed (D-009 blocks mixed
embedding spaces; `POST …/reindex`, D-022). Otherwise nothing changes and the result is recorded
here.

Deviations from the rule's run description, none affecting a gate: the workflow ran on
`windows-2022` (the image CI uses) rather than `windows-latest`, and it is triggered by a
`model-bench/**` branch rather than `bench/**` (which `vector-scale.yml` owns).

Disk: the installed packs are 610 MB (qwen3-embedding) and 605 MB (bge-m3); the vectors stay
1024-d, so the README's free-space figures (3.3 GB for the two default packs, as much again for the
import source) would not change.

**Decision: not adopted.** Condition 5 fails by its letter on one probe; the orchestrator and
gpt-6-sol (high), asked separately, read v2-ans-011 the same way (and agreed that the uncited
refusals on v4-ans-028 and v2-ans-054 and the detector miss on v2-ans-051 are not failures), so
under the owner's rule no arbitration was needed. The default stays `qwen3-embedding-0.6b-q8_0`.

**Reading.** Retrieval-wise bge-m3 is better on every set and cheaper on Metal; what failed is the
answer model's behaviour on a different context: it answered once without citing and with an
added detail. That is a generation problem (answers without `[n]` are not rejected or repaired
today), not an embedder one. The v0.4 holdout is now read for both embedders, so a later bge-m3
decision needs a new unread set; fixing uncited answers first is the cheaper lever and benefits
either embedder.
