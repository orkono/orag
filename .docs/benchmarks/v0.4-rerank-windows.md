# v0.4 reranker on sentence windows (step 65)

Step 63 found rerankers worth up to +8 on v0.2 dev with no loss, and rejected them only on latency
(condition 6: added hybrid p95 ≤ 150 ms on Metal); step 64 showed the cost is the 384-512 tokens
per pair, not the number of decodes. Step 65 scores only a window of each candidate: the sentence
matching the most query-term keys (first 5 characters of each query term of 3+ characters) grown
with its neighbours, at most N characters (`--rerank-window N`, `retrieval/rerank_window.rs`).
A sentence longer than N (a table row, a PDF line) is split at whitespace into halves of the
window first, so a match late in it stays inside. A chunk where no key matches (a cross-language
pair, say) is scored **whole**, not from its start, so no position bias enters; how often that
happens is reported per question (`rerank_whole`) and by category, and its cost counts toward the
latency gate.

## Decision rule (written on 2026-10-15, before any windowed run is scored)

It is not changed after the numbers are in. It is step 63's rule with the window as a new axis.
gpt-6-sol (high) reviewed it and asked for four changes, all taken: (1) wire the reranker into
`orag serve` and `eval answers` before conditions 7-8 are measured, in a fixed order; (2) window
long sentences around the match; (3) score no-match chunks whole and report the rate; (4) state
where this rule differs from step 63's.

**Differences from step 63.** The choice is made only among runs that pass condition 6 (step 63
chose first and then failed on latency); the leader-pinned mode is dropped (it never beat
reranking after promotion in step 63).

**Runs.** Embedder {`qwen3-embedding-0.6b-q8_0` (default), `bge-m3-q8_0`} × reranker
{`qwen3-reranker-0.6b-q8_0`, `bge-reranker-v2-m3-q8_0`} × window {300, 600 characters} × depth
{16, 30}, reranking after leader promotion (step 63's better mode): 16 runs of
`orag eval retrieval` on `eval/corpus/v02` + `v02-retrieval.jsonl`, context budget on, default
lexical mode, engine 0.3.0-alpha.17 build of this branch. The two no-reranker baselines are re-run
on the same build. Only `dev` rows are read until a combination is chosen.

**Choice.** The run with the highest v0.2 dev hybrid in-context W−L against the default
(qwen3-embedding, no reranker), paired per question, **among the runs that pass condition 6**.
Ties: the smaller window, the smaller depth, the default embedder, then the lower measured added
p95.

**Order.** Dev quality and condition 6 choose the run; then the reranker is wired into
`orag serve` and `eval answers` (a separate commit with its own tests) and conditions 7 and 8 are
measured; only then is the v04 holdout read, once, for conditions 2-4. With an embedder change the
full retrieval p95 against today's default is reported too (as in step 63).

**Adopted (opt-in) only if, for the chosen run:**
1. dev in-context W−L ≥ 4;
2. `v04-holdout-retrieval.jsonl`, read once, for the chosen run and the default: W−L ≥ +1;
3. no category loses more than 1 net (v0.2 dev + v04 holdout);
4. factual + identifier + table lose nothing net (same scope);
5. `seed`, `anayasa-tr`, `anayasa-cekim-tr` lose at most 1 each (in context);
6. added hybrid retrieval p95 (with minus without the reranker, same embedder) ≤ 150 ms on this
   M-series Mac (Metal);
7. `orag serve` with the chosen models loaded, RSS after indexing `eval/corpus/v02`, grows by
   ≤ 1 GB against the default;
8. answers (`--sampler dry`) on `v02-answers.jsonl` and `v04-holdout-answers.jsonl`: expected facts
   lose nothing net after a per-probe review of scorer artefacts, and no probe gains an unsupported
   answer or an invalid citation.

If every condition holds the reranker ships as an **opt-in** config key; a default additionally
needs the CPU budget (added p95 ≤ 1500 ms on an x86-64 CPU, measured on the chosen run). An embedder
change forces a reindex, which the release note must say. If no run passes, nothing changes, the
holdout stays unread, and the result is recorded here.

**Condition 6 fails for every run**: the cheapest reranker run (qwen3-embedding + bge-reranker,
window 300, depth 16) still adds 214 ms against the 150 ms budget. Per the rule nothing is chosen,
`orag serve` and `eval answers` are not wired, and **the v04 holdout stays unread.**

**Reading.**
- Windows cut the cost less than expected: qwen3-embedding + bge-reranker after promotion at
  depth 16 added about 302 ms with whole chunks (step 63: p95 316.0 against 13.9 ms) and 214 ms
  (window 300) or 238 ms (window 600) here, at the same +3. The no-match fallback is part of it
  (0.3-12 candidates per question; most in accentless and cross-language questions, where the
  query's keys do not open the passage's words), but the 600-character windows, with under one
  fallback per question in most categories, still cost 238 ms. Token counts and a per-pair cost
  breakdown were not measured, so where the remaining cost goes is not established here.
- The quality picture also changed: **with bge-m3 the reranker adds little.** bge-m3 alone is +5
  (6 wins, 1 loss); the best reranker runs on bge-m3 are +6, one net point more. On the default embedder the best
  reranker run reaches only +3 at depth 16. The gain step 63 measured (+8) came mostly from the
  embedder, and the rest needs depth 30, which costs over 400 ms.
- So the reranker track is closed for v0.4: the lever is the embedder (bge-m3), decided by its
  own rule, written before the v04 holdout is opened and gated on it; bge-m3's known dev +5 is
  exploratory evidence and does not lower Task 44's dev gate of +6. The reranker code stays as an eval-only experiment.
