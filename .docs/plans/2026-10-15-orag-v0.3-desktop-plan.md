# ORAG v0.3 Desktop Application Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A desktop application (macOS, Windows, Linux) that starts the `orag` service, shows the built-in web page in its own window and stops the service when it closes, so a person never opens a terminal or a browser.

**Architecture:** Tauri v2 app in `apps/desktop` (D-016). The `orag` executable ships as a Tauri `externalBin` sidecar and runs `orag serve` with a private home (API and page on `127.0.0.1:0`). A supervisor module reads the two stdout lines (`orag listening on …`, `orag ui on …`), restarts the service on `EXIT_RESTART` (75, setup finished) and on a crash (at most 3 restarts in 60 s), and stops it when the app exits by closing the sidecar's stdin. The window loads the page URL from the second line; that listener serves both `/` and `/v1` and allow-lists its own origin (D-021), so no Tauri origin needs API access.

**Tech Stack:** Rust 2024, Tauri v2 (`tauri`, `tauri-build`, `tauri-plugin-single-instance`, Tauri CLI in CI), the existing `orag` binary, GitHub Actions on macOS 14, Windows 2022, Ubuntu 22.04.

**Spec:** `.docs/orag-decisions.md` D-016 (desktop: Tauri v2, managed sidecar), D-021 (page on a second loopback port), D-023 (setup mode and `EXIT_RESTART`), D-013 (loopback only, no auth), D-012 (offline models), D-017 (versioning), D-020 (workflow).

Reviewed twice by gpt-6-sol (high) on 2026-10-15; its findings are folded in below (Job assignment at process creation on Windows, task order, stdin shutdown on Windows, orphan races, sidecar path contract, webview origin test, early CI lane, release path and tag hand-off).

## Global Constraints

- The service changes only where a task says so (Task 2: `--exit-on-stdin-close`); otherwise the app uses the public CLI, stdout lines and HTTP API.
- Loopback only: the sidecar binds `127.0.0.1:0` for API and page; the app opens no network port of its own and makes no network requests.
- No orphan: when the app exits, crashes or is force-quit, the sidecar stops. Graceful stop = stdin closed (all OSes). Crash fallback: Windows Job Object kill-on-close, assigned at process creation (`PROC_THREAD_ATTRIBUTE_JOB_LIST`), so no instant exists where the child is outside the Job; Linux `PR_SET_PDEATHSIG` plus a parent-pid check right after installing it; macOS the stdin watcher, installed before models load.
- Private home: `<app data dir>/orag` as `ORAG_HOME`, `config.toml` written on first start and kept afterwards; a CLI home is never touched.
- Windows bundle includes the WebView2 offline installer; Linux build floor Ubuntu 22.04 with WebKitGTK 4.1.
- Every merged step bumps `0.3.0-alpha.N` with a CHANGELOG line (D-017); app and service share the version.
- The desktop crate is a workspace member outside `default-members`; the service's `cargo test` does not build it.

## Decision amendments (written in Task 1, before code)

- **D-023:** a D-016 sidecar runs supervised (`ORAG_SUPERVISED=1`): after a model import it exits 75 and the desktop supervisor restarts it, as `orag start` does. Unlike `orag start`, the desktop supervisor also restarts after a crash (3 in 60 s, then an error page).
- **D-012:** the in-app model downloader moves from v0.3 to v0.4. v0.3's app installs models only from offline packs through the existing setup page; the app makes no network request.

## Review Focus

1. Second app launch → the existing window comes to front; no second sidecar fights for the instance lock (single-instance plugin registered before the sidecar starts).
2. Setup import → exit 75 → the window loads the new page URL (new port) without a manual restart.
3. Repeated crashes → after 3 restarts in 60 s an error page with the last stderr lines, not a blank window.
4. App force-quit or crash (including during model load and between spawn and Job assignment) → no `orag serve` process remains; the next launch starts normally.
5. Sidecar that never prints its lines (lock held, stuck start) → after a timeout an actionable error page.

- [ ] Step 4: Containment tests first, with the **real** `orag serve --dev-fake-models`: a parent test process starts the supervisor and is killed hard (`SIGKILL` / `TerminateProcess`), including right after spawn; within 5 s the tracked child pid is gone.
