**Goal:** On a Windows or Linux PC with a compatible discrete Vulkan GPU (NVIDIA, AMD or Intel; integrated GPUs are not used in v0.6), answers come from the GPU, so they take seconds instead of the 1.5–3 minutes they take on the CPU today (4B p50 108 s, 9B p50 194 s on the 4-vCPU reference). A PC without a usable GPU keeps working exactly as in v0.5, with no setup and no error.

**Architecture:** llama.cpp's Vulkan backend (one build for every GPU vendor) in a second service executable, `orag-vulkan`, next to the unchanged CPU `orag`. The desktop supervisor starts `orag-vulkan` when the machine has a working Vulkan GPU and falls back to `orag` when the GPU executable is missing, finds no device, or fails before it is ready. Each executable stays self-contained (D-001); the only new dynamic dependency is the system Vulkan loader (`vulkan-1.dll`, `libvulkan.so.1`), and only `orag-vulkan` has it. Layers are fitted to the GPU's free memory by llama.cpp's own fit routine, so a small GPU gets a partial offload instead of an out-of-memory crash.

**Tech Stack:** Rust 2024, `llama-cpp-2 =0.1.158` features `vulkan` and `common` (for `LlamaModelParams::fit_params`), Vulkan SDK in CI (Windows), `libvulkan-dev` + `glslc` (Ubuntu 22.04), Mesa lavapipe (software Vulkan) for CI tests, Tauri v2 desktop.

**Spec:** `.docs/orag-decisions.md` D-001 (one executable per platform/backend; "Vulkan or CUDA variants later"), D-002 (llama.cpp only), D-012, D-016 (desktop supervisor), D-017 (versioning), D-018 (evaluation before opinions), D-020 (workflow); `.docs/benchmarks/v0.5-model-tiers.md` (tiers and CPU numbers).

## Decisions to approve

**G-1 Backend: Vulkan, not CUDA (for v0.6).** Vulkan covers NVIDIA, AMD and Intel on Windows and Linux with one build and needs only the driver the GPU already has. CUDA is NVIDIA-only, needs `cudart`/`cublas` (hundreds of MB in the installer) or a matching toolkit, and multiplies CI. On NVIDIA, Vulkan is usually somewhat slower than CUDA (to be measured, not assumed: G-7); for ORAG either is a large gain over the CPU path. CUDA stays a later option if measurements show Vulkan falling short on NVIDIA.

**G-2 Packaging: two executables, chosen at start (not a runtime-loaded backend).** Rejected alternative: llama.cpp's dynamic backends (`GGML_BACKEND_DL`: `ggml-vulkan.dll`, `ggml-cpu-*.dll` loaded at run time). It would keep one executable name, but in llama-cpp-sys-2 0.1.158 `dynamic-backends` also turns on `dynamic-link` (`BUILD_SHARED_LIBS`) and `GGML_CPU_ALL_VARIANTS`, so the service becomes an executable plus shared llama/ggml libraries and a directory of backend modules, which breaks D-001's self-contained executable and the static-CRT setup. Crash isolation is not the reason: a supervised one-executable sidecar could also be restarted with the GPU backend disabled. The reasons are packaging (each executable stays one file) and an independent CPU executable that cannot load Vulkan by accident.

Note on `common`: llama-cpp-sys-2's default features include `common`, and `llama-cpp-2`'s `default-features = false` does not turn them off, so the native `common` library is already compiled into today's builds (`cargo tree` shows it). Enabling `llama-cpp-2/common` only exposes the Rust API (`fit_params`). The constraint below is therefore about the CPU build's *configuration and imports*, not about the absence of native `common`. Cost: the desktop bundle carries a second service executable (the CPU `orag` is about 19 MB on macOS today; the Vulkan one is larger because of its compiled shaders, measured in Task 1 and reported before Task 4).

**G-3 Selection and fallback (desktop).** In order:
1. A session state: once this app session has switched to the CPU, every later start and restart in the session stays on the CPU, even if writing the marker failed. Only the retry action (step 6) clears it.
2. Config `gpu = "auto" | "off"` (new key in `config.toml`, default `"auto"`, D-019 read once). `"off"` → CPU. The desktop reads it from the sidecar home's `config.toml` before each start.
3. A persisted fallback marker (`$ORAG_HOME/gpu-fallback.json`: app version, reason, time). It lives in the sidecar's home so the service can report the reason through the API (G-5). It holds the CPU choice while it is for the current app version and younger than 7 days; a new app version, an expired marker, or the setup page's "Ekran kartını yeniden dene" action (deletes the marker, then restarts the sidecar) retries the GPU. A transient driver failure therefore never pins a user to the CPU for good.
4. `orag-vulkan gpu-probe` (hidden subcommand): initialises the Vulkan backend, lists devices (`list_llama_ggml_backend_devices`: name, type, free and total memory) as one JSON line, exits 0. The desktop kills it after 10 s. Exit ≠ 0, a failure to start (missing loader), a timeout, or no discrete GPU with at least 2 GiB of **free** memory → CPU, marker written with the reason. The chosen device's llama device index (`GpuDevice.index` in the probe JSON, not its position in a filtered list) goes to `orag-vulkan serve` as `ORAG_GPU_DEVICE=<n>`.
5. Start `orag-vulkan serve`. Each of these switches to `orag serve` and writes the marker with its reason: exit or crash before `Ready`; no `Ready` within the startup timeout (the child is killed first, `reason=start-timeout`); a **second** crash of `orag-vulkan` in the session at any spacing (`reason=crashed-twice`), so crashes 90 s apart, or slow reloads that never reach "3 in 60 s", still end on the CPU after at most one lost answer. The first crash after `Ready` restarts `orag-vulkan` once. Exit 75 (`EXIT_RESTART`, setup finished) restarts the same backend, is not a crash, and never writes a marker. The backend decision (steps 1–4) runs again on every start and restart. After the switch the normal crash policy (3 in 60 s, then the existing error page) applies to the CPU sidecar; the session state (step 1) means there is no switch back, so the two executables cannot loop.
6. Retry ("Ekran kartını yeniden dene"): shown in the status line of the **main page** (ready mode; the setup page returns early in ready mode, so it is not the place) and on the setup page, only while the CPU is used because of a fallback. The page calls `POST /v1/system/gpu-retry`; only a service started by the desktop supervisor with GPU-retry support (the desktop sets `ORAG_GPU_RETRY=1`; `orag start` sets `ORAG_SUPERVISED=1` but not this, and its launcher restarts only on 75) answers 202 and exits with the new code `EXIT_GPU_RETRY = 76` (distinct from 75, which restarts the same backend); every other service answers 409 and keeps running. On exit 76 the supervisor deletes the marker, clears the session state and the crash count, and starts through the decision (steps 1–5). It is the only way back to the GPU within a session.
Fallback reason: the supervisor keeps the reason in the session state and passes it to the CPU sidecar as `ORAG_GPU_FALLBACK_REASON=<reason>` on every start; the service reports that value (G-5). The marker only carries the reason across app restarts, so a failed marker write loses nothing within the session.
Windows error dialogs: before the first spawn the desktop process calls `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX)` (children inherit it), so a missing `vulkan-1.dll` or a driver fault never shows a system dialog to the user; the child just exits with its status.
Every child the desktop kills (probe or serve) is killed and waited for, so no hung process keeps the GPU. Integrated GPUs are skipped (`type == integrated` → not chosen) until Task 6's measurement shows one faster than the CPU path on the same machine.

**G-4 Offload: llama.cpp fits layers to free GPU memory.** Only in the `vulkan` build (all fit code under `#[cfg(feature = "vulkan")]`; the CPU and Metal builds keep today's `load_model`). The fit must see the context each role really creates, so each role's context parameters are built by one function used both for the fit and for context creation: `embedder::context_params(spec)` (embeddings on, `n_ctx = n_batch = n_ubatch = max_tokens`, pooling), `generator::context_params(spec)` (`n_ctx`, `n_batch = PROMPT_BATCH`), `reranker::context_params(spec)` (embeddings on, rank pooling, `n_ctx = n_batch = n_ubatch`). `load_model(path, &LlamaContextParams)` takes that value (all three callers change):
- starts from `LlamaModelParams::default()` (no `with_n_gpu_layers` before the fit: `fit_params` only fits default-valued fields), restricted to the chosen device with `with_devices(&[ORAG_GPU_DEVICE])`, so an integrated GPU is never part of a split;
- fits against a copy of the role's `LlamaContextParams` (its `n_ctx` is non-zero, so the fit sizes the KV cache and compute buffers for the real context and never shrinks it) and passes `n_ctx_min` equal to that `n_ctx`; the context is then created from the same function's value, never from a fit-modified copy;
- passes `margins` of length `llama_max_devices()`, 512 MiB each;
- loads with the fitted params object (it owns the `tensor_split` and buffer-override arrays it points to).
**CPU-only load** means fresh `LlamaModelParams::default().with_devices(&[])` (an empty, null-terminated device list: the model has no GPU device, so context creation initialises no Vulkan backend and the scheduler cannot move operations of CPU-resident weights onto a GPU; `n_gpu_layers = 0` alone is not enough because `op_offload` defaults to true and context creation still initialises the model's GPU devices). `FitError::Failure` (does not fit) → CPU-only load, log `gpu_offload=none reason=fit_failed`; `Ok` with zero layers on the GPU → the same CPU-only load, `reason=fit_zero_layers` (a fit result whose lower bound is zero layers is valid upstream behaviour, not an error); `FitError::Error` (unreadable model, other hard error) → returned as an error, never masked as a CPU load. Models load one after another (embedder, generator, reranker, as `app.rs` does today), because the fit call changes llama.cpp's global logger and is not thread-safe; each fit sees the memory the previous model took. `model_info()` is unchanged: it loads with 0 GPU layers, as today, and never fits. The fit is an estimate from a snapshot of free memory, which another program can change before allocation: a failure to load the model or to create its context after a successful fit is retried once as a CPU-only load (`gpu_offload=none reason=alloc_failed`); an error after that is returned. Each loaded model records its outcome (`layers_on_gpu`, `layers_total`, device name) for G-5.
Standalone `orag-vulkan serve` (CLI, no desktop): `ORAG_GPU_DEVICE` set → that device (an invalid index is a startup error with a clear message); unset → the same choice rule as the probe (discrete, most free memory, ≥ 2 GiB free); no eligible device → every model is a CPU-only load and the log says why. `gpu = "off"` in `config.toml` → CPU-only loads regardless of the variable. Precedence: `gpu = "off"` > `ORAG_GPU_DEVICE` > automatic choice.

**G-5 What the page says.** The source of truth for "GPU in use" is the running service's actual offload (G-4's per-model outcome), never the marker: `in_use` is true only when the generator has layers on a GPU (`layers_on_gpu == layers_total` → "kullanılıyor", fewer → "kısmen kullanılıyor"). The marker only supplies the *reason* when the desktop fell back (`reason` is null only when the CPU is used by choice: `gpu = "off"` or the CPU `orag` run directly; when the desktop chose the CPU because of a failed or empty probe, including no eligible device, the marker's reason is shown). The setup page's machine card shows "Ekran kartı: <name> — kullanılıyor / kısmen / kullanılmıyor (<reason>)" and the speed hint uses the new `gpu_p50_answer_s` only when the generator is fully on the GPU. Tier RAM thresholds stay as in v0.5 (conservative: with full offload system RAM use drops, but a partial offload still needs it). The verdict does not use VRAM in v0.6.

**G-6 CLI.** The CLI archives for Windows and Linux contain both `orag` and `orag-vulkan`. `orag start` and `orag serve` stay CPU; README documents `orag-vulkan serve` for a GPU. No automatic switching in the CLI in v0.6 (the desktop app is the audience that must not configure anything).

**G-7 Measurement.** No GPU is available to the project's CI or to the rented server (toprakhan has a virtual VGA only). Correctness is gated in CI with Mesa lavapipe (software Vulkan, slow; its results differ from the CPU in the last bits, as Metal's do (D-005), so its gate is a tolerance, not equality). In CI lavapipe is made the only Vulkan device (`VK_ICD_FILENAMES`/`VK_DRIVER_FILES` pointing at its ICD alone) and selected explicitly with `GGML_VK_VISIBLE_DEVICES=0`: ggml-vulkan skips CPU-type physical devices by default and, once admitted, reports lavapipe as a GPU-type device. Tests assert a real offload (`layers_on_gpu > 0` and the Vulkan buffer in the load log), so a silent CPU load cannot pass. Speed and correctness on real hardware are measured on the owner's Windows PC with a `0.6.0-alpha` desktop build, by a hidden bench action that runs the same models and questions on both executables (paired CPU and Vulkan runs), cold (first answer after start) and warm reported separately, with the shipped generation tiers. **GPU support does not leave alpha without that real-GPU validation:** if the owner's PC has no supported GPU, 0.6.0 ships without `orag-vulkan` in the stable bundles (the GPU build stays in the pre-release) until a GPU machine has passed Task 6's gate.

## Global Constraints

- The CPU `orag` executable is byte-for-byte the same build configuration as v0.5 (no new features, no new dynamic dependencies); `check-binary-deps.sh` unchanged for it.
- `orag-vulkan` may import exactly one non-system library: `vulkan-1.dll` (Windows) or `libvulkan.so.1` (Linux). `check-binary-deps.sh` gets a per-executable allow-list.
- macOS is unchanged (Metal, one executable). No `orag-vulkan` on macOS.
- A PC without a Vulkan loader or GPU must start the desktop app exactly as v0.5 does: same first screen, no error dialog, at most 10 s extra on first start (the probe timeout), 0 s on later starts (marker).
- The first answer on Vulkan includes shader pipeline creation after `Ready`; the page already waits for a slow answer, and the measurement (Task 6) reports the first answer separately.
- Every merged step bumps `0.6.0-alpha.N` with a CHANGELOG line (D-017); steps are numbered from 83.
- Workflow D-020: branch per step, TDD, gpt-6-astra review before push, merge `--no-ff`.

## Review Focus

1. Windows PC with no Vulkan loader (`vulkan-1.dll` absent: VMs, Windows Server, basic display driver) → `orag-vulkan` cannot even start (loader error 0xC0000135) → CPU sidecar, no dialog, marker written.
2. GPU with little memory (2–4 GiB) and the 9B tier → partial offload, not an out-of-memory abort; answers still correct.
3. A driver that hangs in `vkCreateDevice` → probe timeout → CPU, the app window is not blocked.
3a. A missing `vulkan-1.dll` or a driver fault shows no Windows system dialog (error mode set before spawning).
4. The GPU sidecar crashes mid-answer after `Ready` → the question returns an error the page can retry and `orag-vulkan` restarts once; a second crash at any later time → CPU for the rest of the session; never a loop between the two executables.
5. Two GPUs (laptop iGPU + dGPU) → the discrete one is chosen; the integrated one is not used for split.

## Risks

- **Vulkan SDK in CI build time:** shader generation adds minutes to every Windows/Linux build. Mitigation: only the `orag-vulkan` job builds it, with its own cache key.
- **Installer size:** grows by the Vulkan executable's size (measured in Task 1).
- **Driver bugs:** some old drivers expose Vulkan 1.1 without features llama.cpp needs; the probe then fails or the sidecar crashes, and G-3 falls back. Covered by Review Focus 1, 3, 4.
- **No GPU to test in CI:** lavapipe proves the code path, not the speed; G-7 depends on one real machine.
