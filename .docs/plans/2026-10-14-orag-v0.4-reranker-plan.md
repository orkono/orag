# ORAG v0.4 Reranker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (the owner chose native execution: the orchestrator implements every task itself). Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** written 2026-10-14 (step 61). Execution starts after this plan is merged; decisions
inside it follow the owner's protocol (orchestrator + gpt-6-sol high agree → decided; otherwise
the owner arbitrates).

**Goal:** Measure whether a local cross-encoder reranker over the fused candidates gets more
evidence into the answer context than today's deterministic hybrid, and adopt it (opt-in or
default) only if a rule written before scoring says so.

**Architecture:** A new `Reranker` trait beside `Embedder` and `Generator`, a llama.cpp
implementation with rank pooling (`LlamaPoolingType::Rank`, present in llama-cpp-2 0.1.158), a
fake for tests, and one optional step in `Retriever::retrieve` that re-orders the first
`rerank_depth` fused hits by reranker score. Off unless configured; the eval can switch it on
per run.

**Tech Stack:** Rust, llama-cpp-2 =0.1.158 (Metal on macOS, CPU elsewhere), GGUF model packs.

**Spec:** `.docs/orag-decisions.md` D-005 (no decision models in v1; reranker a v0.4+
candidate), D-007 (Qwen3-Reranker-0.6B on 20 candidates, bge-reranker-v2-m3 challenger,
off by default), D-018 (eval sets; v0.4 holdout read once per chosen candidate).

## Why, and what the evidence says

On the rewritten v0.2 set with the 0.3.0-alpha.13 engine hybrid in context is 0.931. The step 51
diagnosis (`.docs/benchmarks/v0.3-lexical-stems.md`) splits misses into **near** (a list ranks
the label within 10, fusion drops it), **deep** (best list rank 12-49) and **absent**. Fusion
re-orderings without a model failed twice (steps 50, 57). A reranker is the only lever that
reads query and passage together; it can lift near and deep labels that are already among the
first 20 fused candidates, and cannot help absent ones. bge-m3 (step 59) is a separate lever
(the embedder) and is decided first, so the reranker is measured on top of the winner.

## Review Focus

1. Failure handling, consistent with D-019: a configured `reranker_model` whose pack is missing
   or invalid is a startup config error, like any bad key. A scoring failure or a timeout at
   request time (`rerank_timeout_ms`) falls back to the fused order for that question and logs
   once; the answer never fails because of the reranker. Pinned in Tasks 3 and 4.
2. Scores for very long passages: the reranker's context is smaller than a chunk plus question
   at times; truncation must keep the question whole and cut the passage, never panic. Task 2.
3. Ties and NaN scores must keep the fused order (stable sort, NaN last). Task 3.
4. Latency: 20 pairs per question on CPU (Windows/Linux) may be seconds; the rule's latency
   condition is measured on both the M-series Mac and the CI Linux runner. Task 6.
5. Determinism: the same question gives the same order on repeated runs (batch order fixed,
   no sampling). Task 3.
6. Prompt injection into the reranker template: question and passage text go through the
   existing special-token guard (`infer/prompt.rs`) before a Qwen3-Reranker template is filled,
   so a document cannot close the template. Task 2.

### Task 0: One holdout read for the whole v0.4 retrieval decision

The v0.4 holdout is read **once** for retrieval (D-018). So the embedder and the reranker are not
confirmed separately: the rule in Task 6 covers the combinations {qwen3-embedding, bge-m3} ×
{no reranker, each qualified reranker variant}, all scored on v0.2 `dev`; the single best
combination is then read once on `v04-holdout-retrieval.jsonl`. bge-m3 dev scores can be taken
now (no code); its holdout read waits for Task 6.

### Task 1: `Reranker` trait and fake

- [ ] Write failing tests in `infer/fake.rs`: `FakeReranker` scores a passage containing every
  query term above one containing none; equal passages get equal scores; empty `passages`
  returns an empty vector.
- [ ] Add the trait to `infer/mod.rs` and `FakeReranker`; tests pass.
- [ ] Commit `feat: add a reranker trait and a fake for tests`.

### Task 2: llama.cpp reranker

- [ ] Fetch candidate packs into `~/orag-packs/_candidates/` (Qwen3-Reranker-0.6B Q8_0 GGUF,
  bge-reranker-v2-m3 Q8_0 GGUF) with checksums and licenses recorded in the benchmark doc.
- [ ] Write `tests/reranker_qualification.rs` (skipped without the pack): for 10 triples
  (query, relevant, distractor) from `eval/corpus/v02`, the relevant passage scores higher in at
  least 9; scores are finite; Metal and CPU scores agree within 1e-3 after sigmoid; a passage
  longer than the context is truncated without error, the question kept whole.
- [ ] Implement `infer/llama/reranker.rs` with `LlamaPoolingType::Rank`, one sequence per pair,
  batched. Rank pooling returns `n_cls_out` values per sequence (llama-cpp-2 `context.rs`), and
  for Qwen3 llama.cpp applies a softmax over the classifier outputs: the pack's `[reranker]`
  section names the output index that means "relevant" (Qwen3: the `yes` class; bge: the single
  logit), and qualification checks that index, and that the ordering of the 10 triples matches
  a reference ordering recorded from the model card's own example code (run once, outside ORAG,
  and committed as fixture data). Qwen3-Reranker uses its documented query/document template,
  filled only after the special-token guard. A candidate that fails qualification is recorded as "not qualified at llama-cpp-2
  0.1.158" and not scored.
- [ ] Commit `feat: run cross-encoder rerankers with llama.cpp rank pooling`.

### Task 3: Rerank step in retrieval

- [ ] Failing tests in `retrieval/hybrid.rs` with `FakeReranker`: with `rerank: None` the order
  is byte-for-byte today's; with depth 20 only the first 20 fused hits are re-ordered and the rest
  keep their place; ties and NaN keep fused order; repeated calls give the same order.
- [ ] Today `retrieve` cuts the fused list to `limit` before hydration (`hybrid.rs`), and the
  answer path asks for 16. With a reranker, hydrate and score `max(rerank_depth, limit)` fused
  candidates first, then cut to `limit`, so a candidate at 17-30 can still reach the context.
  Test: with depth 30 and limit 16, a candidate fused at 25 that the fake scores highest comes
  first.
- [ ] Implement `rerank_fused` after leader promotion. Measure two variants in Task 6: rerank
  after promotion (leaders can lose their slot) and rerank with leaders pinned. A score error or
  `rerank_timeout_ms` (default 2000) falls back to the fused order (test with a failing fake).
- [ ] Commit `feat: optionally rerank the first fused candidates`.

### Task 6: Decision rule, then scoring

- [ ] Write and commit the rule in `.docs/benchmarks/v0.4-reranker.md` before any real-model
  score. Proposed (to be agreed by orchestrator + gpt-6-sol when the task starts): combinations
  are {qwen3-embedding, bge-m3} × ({no reranker} ∪ each qualified reranker × {after promotion,
  leaders pinned} × depth {16, 20, 30}), against today's default; the combination with the
  highest v0.2 dev in-context W−L is chosen; it is adopted only if (1) dev W−L ≥ 4 (many
  variants: a stricter bar against picking noise); (2) on `v04-holdout-retrieval.jsonl`, read
  once, W−L ≥ +1 (a real gain, not just no loss); (3) no category loses more than 1 net over
  both; (4) factual + identifier + table lose nothing net; (5) seed and Anayasa guard sets lose at
  most 1 each; (6) **added** retrieval p95 (with minus without reranker, same 20-pair depth,
  single client, warm model) ≤ 150 ms on the M-series Mac and ≤ 1500 ms on the reference CPU
  (8-core x86-64 Linux, the vector-scale reference); (7) `orag serve` RSS grows by ≤ 1 GB;
  (8) answers on v0.2 and v0.4 probes lose no expected facts net after a per-probe check of
  scorer artefacts. An embedder change also needs the reindex noted in the release.
- [ ] Score dev, choose, read the v0.4 holdout once, run guards and answers; record everything.
